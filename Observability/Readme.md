## What is Observability?

Observability is the ability to understand the internal state of a system by analyzing the data it generates.

In modern cloud-native applications, observability helps engineers monitor system health, troubleshoot issues, optimize performance, and understand how services interact with each other.

Observability is built on three key pillars:

### Metrics (tells us what is happening)

Metrics are numerical measurements collected over time that help monitor application and infrastructure performance.

Examples:

* CPU Utilization
* Memory Usage
* Request Rate
* Error Rate
* Response Time

In this project, metrics are collected using **Prometheus** and visualized using **Grafana**.

### Logs (explains why it is happening)

Logs are timestamped records generated by applications and infrastructure components.

They provide detailed information about system events and application behavior.

Examples:

* Application Errors
* User Activity
* API Requests
* System Events

Logs help identify root causes during troubleshooting.

### Traces (shows how it is happening)

Distributed traces track a request as it travels across multiple services in a microservices architecture.

Tracing helps engineers:

* Understand service dependencies
* Identify bottlenecks
* Measure request latency
* Debug failures across services

In this project, traces are collected using **OpenTelemetry** and visualized using **Jaeger**.

## Monitoring vs Observability

Although the terms Monitoring and Observability are often used interchangeably, they serve different purposes.

| Monitoring                                               | Observability                                                      |
| -------------------------------------------------------- | ------------------------------------------------------------------ |
| Focuses on known issues and predefined metrics.          | Focuses on understanding unknown issues and system behavior.       |
| Answers: "Is something wrong?"                           | Answers: "Why is it wrong?"                                        |
| Relies on dashboards, alerts, and predefined thresholds. | Uses metrics, logs, and traces to investigate problems.            |
| Detects failures and performance degradation.            | Helps identify the root cause of failures.                         |
| Best suited for known scenarios.                         | Best suited for complex distributed systems and unknown scenarios. |

### Monitoring Example

A Grafana dashboard shows that CPU utilization has exceeded 90%.

Monitoring tells us:

* CPU usage is high.
* An alert is triggered.
* The application may be impacted.

However, monitoring does not explain why CPU usage increased.

### Observability Example

Using OpenTelemetry, Prometheus, Grafana, and Jaeger, we can investigate:

* Which service caused the spike?
* Which request generated the load?
* Which microservice is experiencing latency?
* What is the root cause of the issue?

Observability provides the context required to answer these questions.

### Relationship Between Monitoring and Observability

Monitoring is a subset of Observability.

Monitoring helps detect problems, while Observability helps explain and resolve them.

In this project:

* Prometheus collects application and infrastructure metrics.

Together, these tools create a complete Observability platform for cloud-native applications running on Amazon EKS.

Prometheus collects and stores metrics as time-series data, allowing teams to monitor application performance, infrastructure health, and system behavior in real time.

### Key Features

* Time-Series Metrics Collection
* Kubernetes Service Discovery
* Powerful Query Language (PromQL)
* Alerting and Notifications
* Multi-Dimensional Data Model
* Cloud-Native Monitoring

1. Prometheus periodically scrapes metrics from configured targets.
2. Metrics are stored in a time-series database.
3. PromQL is used to query and analyze collected data.
4. Grafana connects to Prometheus to visualize metrics through dashboards.
5. Alertmanager can be integrated to generate alerts based on predefined rules.

## PromQL (Prometheus Query Language)

PromQL is the powerful query language used by Prometheus to retrieve, analyze, and manipulate time-series metrics data.

It enables users to perform real-time monitoring, troubleshooting, and performance analysis by querying metrics collected from applications and infrastructure.

### Why PromQL is Important

PromQL helps engineers:

* Monitor system performance
* Analyze application behavior
* Create Grafana dashboards
* Troubleshoot issues
* Build alerting rules
* Track resource utilization

### Basic PromQL Syntax

PromQL queries are built using metrics collected by Prometheus.

Example:

```promql
up
```

This query shows whether monitored targets are currently available.

---

### Common PromQL Queries

#### CPU Usage

```promql
rate(container_cpu_usage_seconds_total[5m])
```

Displays CPU usage over the last 5 minutes.

#### Memory Usage

```promql
container_memory_usage_bytes
```

Shows current memory consumption of containers.

#### Pod Count

```promql
count(kube_pod_info)
```

Returns the total number of pods running in the cluster.

#### Node CPU Utilization

```promql
100 - (avg by(instance)(rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)
```

Displays CPU utilization percentage for cluster nodes.

#### Request Rate

```promql
rate(http_requests_total[5m])
```

Shows the number of requests processed per second.

#### Error Rate

```promql
rate(http_requests_total{status=~"5.."}[5m])
```

Displays the rate of server-side errors.

---

### Aggregation Functions

PromQL provides powerful aggregation functions:

#### Sum

```promql
sum(container_memory_usage_bytes)
```

Calculates total memory usage.

#### Average

```promql
avg(container_cpu_usage_seconds_total)
```

Calculates average CPU usage.

#### Maximum

```promql
max(container_memory_usage_bytes)
```

Shows highest memory consumption.

#### Count

```promql
count(kube_pod_info)
```

Counts matching metrics.

Examples:

* Faster setup

## Types of Metrics in Prometheus

Prometheus stores data as time-series metrics. Every metric consists of a metric name, labels, timestamp, and value.

Prometheus supports four primary metric types:

### 1. Counter

A Counter is a cumulative metric that only increases over time or resets when the application restarts.

Use Cases:

* Total Requests
* Total Errors
* Processed Transactions
* API Calls

Example:

```promql
http_requests_total
```

Characteristics:

* Value can only increase.
* Cannot decrease.
* Useful for counting events.

---

### 2. Gauge

A Gauge represents a value that can increase or decrease over time.

Use Cases:

* CPU Usage
* Memory Consumption
* Active Connections
* Queue Length

Example:

```promql
container_memory_usage_bytes
```

Characteristics:

* Can increase or decrease.
* Represents current state measurements.

---

### 3. Histogram

A Histogram measures the distribution of observations by grouping values into configurable buckets.

Use Cases:

* Request Duration
* Response Size
* Database Query Latency

Example:

```promql
http_request_duration_seconds_bucket
```

Characteristics:

* Stores observations in buckets.
* Calculates percentiles and latency distributions.
* Useful for performance analysis.

Example Query:

```promql
histogram_quantile(0.95, rate(http_request_duration_seconds_bucket[5m]))
```

Calculates the 95th percentile response time.

---

### 4. Summary

A Summary captures statistical information such as quantiles over a sliding time window.

Use Cases:

* Request Latency
* Response Time Analysis
* Performance Monitoring

Example:

```promql
http_request_duration_seconds
```

Characteristics:

* Calculates quantiles directly.
* Less flexible than Histograms for aggregation.
* Useful for application-level latency tracking.

---

## Comparison of Metric Types

| Metric Type | Can Increase | Can Decrease | Supports Quantiles | Common Use Case               |
| ----------- | ------------ | ------------ | ------------------ | ----------------------------- |
| Counter     | ✅            | ❌            | ❌                  | Request Count, Error Count    |
| Gauge       | ✅            | ✅            | ❌                  | CPU, Memory, Active Users     |
| Histogram   | ✅            | ✅            | ✅                  | Request Duration Distribution |
| Summary     | ✅            | ✅            | ✅                  | Response Time Percentiles     |

## Jaeger

Jaeger is an open-source distributed tracing platform used to monitor and troubleshoot microservices-based applications. It helps developers and operations teams understand how requests flow through distributed systems and identify performance bottlenecks.

Originally developed by Uber and now a CNCF graduated project, Jaeger is widely used in cloud-native environments alongside OpenTelemetry.

### Why Jaeger?

In a microservices architecture, a single user request may travel through multiple services before a response is returned.

Without tracing, it becomes difficult to determine:

* Which service is causing latency?
* Where did the request fail?
* Which downstream service is slow?
* How are services interacting?

Jaeger provides end-to-end visibility into request execution.

---

### Key Features

* Distributed Tracing
* Request Flow Visualization
* Service Dependency Analysis
* Root Cause Analysis
* Performance Monitoring
* Latency Investigation
* OpenTelemetry Integration

---

### Core Components of Jaeger

#### Client

Applications generate trace data using OpenTelemetry instrumentation.

#### Agent

Receives trace data from applications and forwards it to Jaeger components.

#### Collector

Processes and stores traces.

#### Query Service

Retrieves trace information and serves it through the Jaeger UI.

#### Jaeger UI

Provides a web interface for visualizing and analyzing traces.

---

### Important Jaeger Concepts

#### Trace

A trace represents the complete journey of a request across multiple services.

Example:

```text id="e7wgvk"
User Request
     │
     ▼
Frontend Service
     │
     ▼
Product Service
     │
     ▼
Payment Service
     │
     ▼
Response
```

The entire flow is called a Trace.

---

#### Span

A span represents a single operation within a trace.

Example:

```text id="lxpmcg"
Trace
 ├── Frontend Span
 ├── Product Service Span
 ├── Payment Service Span
 └── Database Span
```

Each service generates one or more spans.

---

#### Parent Span

The operation that initiates another operation.

#### Child Span

The operation triggered by a parent span.

This relationship helps visualize request dependencies.
